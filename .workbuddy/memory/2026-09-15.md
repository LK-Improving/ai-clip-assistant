## 修复 `pnpm make` 打包报错 `Authors is required`

- **现象**：`pnpm make` 时 zip 与 squirrel 两个 maker 都 ✖，根因是 Squirrel 生成器（electron-winstaller）拼 `.nuspec` 时缺必填 `authors` 字段，抛未处理异常导致整个 make 进程崩溃，并行跑的 zip maker 被牵连标记失败。

- **注意**：`pnpm make` 走 `apps/desktop/scripts/forge.cjs`（自动选 Node>=22.12）；Windows 产 zip + Squirrel 安装器；代码签名需 `CSC_LINK` 等环境变量，缺了只是不签名、不影响打包。

## 修复 `pnpm make` 打包第二阶段报 `EBUSY: resource busy or locked, unlink ...app.asar`

- **现象**：`authors` 修复后，用户本机重跑 `pnpm make` 在 `Packaging for x64 on win32` → `Copying files / Finalizing package` 阶段再报 EBUSY，锁的是 `out/MiaomaStudio-win32-x64/resources/app.asar`。沙箱与本机都复现，是真问题（非沙箱特例，之前误判过一次）。
- **根因**：用户第一次跑其实**打包成功**（能进 Squirrel 步骤就证明 app.asar 已生成）；重跑时 Forge 先清理已存在的 `out` 目录，而那个**旧 app.asar 被 Windows Defender 实时扫描锁住句柄**，`unlink` 失败 → EBUSY。第一次能成功是因为当时 out 目录不存在、无需清理旧 asar。
- **修复（环境侧，非业务代码）**：① 给项目目录加 Defender 排除项：`Add-MpPreference -ExclusionPath "D:\Study\重点项目\AI剪映"`（PowerShell 管理员）；② `Remove-Item -Recurse -Force apps/desktop/out`；③ 重跑 `pnpm make`。排除后 Defender 不再锁新 asar，删除+重建即过。
- **代码侧**：仅在 `forge.config.ts` 的 `packagerConfig` 加了该坑的注释说明（行为不变）。未改 `asar:true`（保持产品形态）。
- **教训**：Electron Forge 打包在 Windows 上受实时杀软影响是通病；EBUSY 在 app.asar 上几乎都指向 Defender 锁文件，第一反应是加排除项+清 out，而不是改代码。

## 修复 `pnpm make` 第三阶段 Squirrel 报 `rcedit.exe ... Fatal error: Unable to load file`

- **现象（EBUSY 修好后）**：zip maker 已 ✔（16s），但 Squirrel maker 失败 `exit 4294967295`，rcedit.exe 给 `out/make/squirrel.windows/x64/Setup.exe` 写版本信息/图标时报 `Unable to load file`。错误里路径是乱码 `D:\Study\�ص���Ŀ\AI��ӳ\...`（即中文项目路径 `D:\Study\重点项目\AI剪映`）。
- **根因**：electron-winstaller 调用的原生工具 `rcedit.exe` 无法按正确编码解析**中文路径**下的 `Setup.exe`（zip maker 不调原生 PE 工具所以能过）。这是上游 rcedit 对 CJK 路径的已知缺陷。
- **修复（不改业务、不动项目目录）**：在 `apps/desktop/forge.config.ts` 把 Forge 顶层 `outDir` 重定向到纯英文绝对路径 `D:/miaoma-build`，让 `Setup.exe` 落在 ASCII 路径上；同时**去掉 Squirrel maker 的 `setupIcon`**（其图标路径 `assets/icon.ico` 也是中文，会二次触发同样的 `Unable to load file`）。应用 exe 图标仍由 `packagerConfig.icon` 设置（electron-packager 复制文件不受中文路径影响）。
- **验证**：沙箱与本机共享磁盘+Defender，可直接在沙箱 `pnpm make` 复现/验证。
- **教训**：凡 Electron Forge 调用原生 Windows 工具（rcedit / squirrel / signtool）的环节，中文项目路径都会踩坑；通用解法是 `outDir` 指到 ASCII 路径，或把整个项目移到英文目录。安装器自定义图标要等项目迁到英文路径后再加回 `setupIcon`。

## 修复 `pnpm make` 报 `The "paths[0]" argument must be of type string. Received undefined`（NSIS maker 与 Forge 7.11 接口不兼容）

- **背景**：Squirrel 安装器会静默装到 `%LOCALAPPDATA%`、不符合「给别人用」的预期，用户选了 **NSIS 向导式安装包**（装到 Program Files + 开始菜单/桌面快捷方式 + 可选目录）。阶段五随之从 Squirrel 切到 `electron-forge-maker-nsis`（electron-builder 的 nsis target 封装，官方 Forge 7 无 maker-nsis）。
- **现象**：把 maker 换成 `electron-forge-maker-nsis` 后，`pnpm make` 在启动阶段（Resolving make targets）即崩：`The "paths[0]" argument must be of type string. Received undefined`。
- **根因**：`electron-forge-maker-nsis` v26 的 `main.js` 仅 `exports.default = function(options){ return buildForge(options, {win:[`nsis:${options.targetArch}`]}) }` —— 是个**普通函数**，不是 maker「类」。Forge 7.11 在 `make.js:98` 用 `new MakerClass(resolvableTarget.config, ...)` 实例化每个 maker；对普通函数 `new` 会**立即执行**它，于是 `buildForge` 里 `path.resolve(options.dir)` 的 `dir` 是 `undefined`（Forge 还没把已打包 app 目录喂进来）→ 抛 `paths[0] undefined`。配套确认：`app-builder-lib/out/forge-maker.js` 的 `buildForge(forgeOptions)` 第一行就是 `path.resolve(forgeOptions.dir)`；`@electron-forge/maker-base` 的 `Maker` 基类靠 `__isElectronForgeMaker` 标记 + `make(opts)` 方法区分。
- **修复（新增本地 wrapper，不改 npm 包）**：新建 `apps/desktop/makers/nsis-maker.cjs`，继承 `@electron-forge/maker-base` 的 `Maker`（取 `MakerBase||default||Maker` 兼容不同版本导出名），`name='nsis'`、`defaultPlatforms=['win32']`、`isSupportedOnCurrentPlatform()=>process.platform==='win32'`、`make({dir,makeDir,targetArch})` 内调 `buildForge({dir}, {win:[`nsis:${targetArch}`], config:{appId, directories:{output:makeDir}, ...userConfig}})`。关键：把 Forge 给的**已打包 app 目录** `dir` 作为 `buildForge` 的 `forgeOptions.dir`，让 `path.resolve` 拿到真实字符串；输出目录对齐 Forge 约定的 `makeDir`。
- **接入**：`forge.config.ts` 的 makers 里把 `name: 'electron-forge-maker-nsis'` 改为 `name: './makers/nsis-maker.cjs'`（相对路径被 `import-search.js` 解析为该文件；其 `module.exports` 默认导出是真正的类，`new` 后正常）。`getAppBuilderConfig` 返回的 NSIS 选项必须**放在 `nsis` 子键下**——electron-builder 26 的 schema 已不再接受根级 `oneClick/perMachine/allowToChangeInstallationDirectory/createDesktopShortcut/createStartMenuShortcut`（否则报 "unknown property"）。`apps/desktop/package.json` 新增直接依赖 `app-builder-lib`（之前只是 `electron-forge-maker-nsis` 的传递依赖，显式声明以防该包被移除后 wrapper 找不到）。
- **验证**：`pnpm make`（走 `scripts/forge.cjs`，Node>=22.12）→ `Making a nsis distributable for win32/x64` → `electron-builder version=26.15.3` → `building target=nsis file=D:\miaoma-build\make\MiaomaStudio-Setup-0.1.0.exe archs=x64 oneClick=false perMachine=true` → `MAKE_EXIT=0`。产物：向导式 `MiaomaStudio-Setup-0.1.0.exe`（约 133MB，含完整 ffmpeg）落到 `D:/miaoma-build/make/`；zip 便携版同时在 `D:/miaoma-build/make/zip/`。日志中 `default Electron icon is used` 仅为安装器图标告警（app exe 图标由 `packagerConfig.icon` 设置），不影响功能。
- **结论**：秒剪 Studio 现在 `pnpm make` 即可产出「给别人用」的 NSIS 向导式安装包。未签名时用户首次运行会被 SmartScreen 拦截，点「仍要运行」即可（之前已科普：闭源/个人场景无免费消除 SmartScreen 的证书；U盘/局域网拷贝可绕开 MOTW）。
